## 1. 验证是否能够通过 GitHub 在 DSH 进行插件的安装

**现状**：`README.md` / `docs/安装说明.md` 的安装方式只有两种——指向本地仓库目录，或指向本地 `.tgz` 完整路径。`package.json` 里已有 `repository` 指向 `github.com/zzhiyoung/DSH-plugin`，但从未验证过「包名或地址」能否直接吃 GitHub 地址。

**要核实的**

- [ ] 「添加插件」→「包名或地址」逐种试填：仓库 URL、`git+https`、分支 tarball URL、Release 里的 `.tgz` 链接、npm 包名；记录每种的成功与否和报错原文。
- [ ] 若支持：确认是否需要公开仓库或 token、是 clone 还是走 `npm install`、`peerDependencies` 如何解析、装完后的版本号与启用流程是否和本地安装一致。
- [ ] 若不支持：确认最接近的替代路径（下载 Release 产物后填本地路径 / 自建 npm 源），以及是否需要改 `package.json` 的 `dsh` 字段或新增 manifest。
- [ ] 先排除本机网络因素（代理、DNS）造成的假失败，区分「DSH 不支持」和「网络层不通」两类结论。

**验收**：给出明确结论与可用的填法；支持则更新 `README.md`「安装」和 `docs/安装说明.md` 的安装步骤。

**关联**：`README.md` 安装章节、`docs/安装说明.md`、`package.json`（`repository` / `dsh.bundle` / `files`）。

## 2. 安装过程灵活探测本机可接入 Agent，选出最合适的可执行程序或 CLI

**现状**：探测逻辑按 `id` 硬编码在根 `index.js`，只有 WorkBuddy 有真正的查找（`DSH_ACP_WORKBUDDY` → Program Files / `%LOCALAPPDATA%\Programs` → 卸载注册表）；Codex 靠内置适配器加 `CODEX_PATH`，Qoder 靠默认路径或 `DSH_ACP_QODER`。新增 agent 要手写路径，且 `package.json` 只声明 `platforms: win32`。

**要做的**

- [ ] 确认探测发生的时机：DSH 是否提供安装期钩子；若没有，则放在插件首次启用 / 加载时，并把结果持久化到配置，避免每次启动重复扫描。
- [ ] 梳理候选来源：`PATH`、常见安装目录、注册表卸载项、各 CLI 的默认配置目录、已登录账号的痕迹。
- [ ] 设计统一的发现器：按 agent 类型产出「可执行文件路径 + 启动参数 + 是否需 `authenticate`」的候选清单，不再按 id 写死分支。
- [ ] 对候选做 ACP 能力探测（复用 `scripts/probe-acp.mjs` 的握手：协议版本、模型目录、登录方式、`session/new`），按可用性排序，自动选最优或让用户在安装阶段确认。
- [ ] 探测失败时给出可操作的提示（缺哪个 CLI、去哪登录、该设哪个环境变量），不要静默跳过整行。
- [ ] 明确跨平台边界：当前只支持 `win32`，是否一并支持 macOS / Linux 的探测路径。
- [ ] 补单元测试（参考 `test/` 现有桩），覆盖「找到 / 找不到 / 多个候选」三种情况。

**验收**：在未设置任何 `DSH_ACP_*` 环境变量的机器上，安装后能自动列出并启用本机实际存在的 ACP agent；`cordis.patch.yml` 里 `command` 留空即可完成补全。

**关联**：`index.js`（`locateWorkBuddy` / `planWorkBuddy`）、`codex-desktop.mjs`、`cordis.patch.yml`、`scripts/probe-acp.mjs`、`src/index.js`。

## 3. 排查 WorkBuddy 接入失败，修复后对比模型与费率

**现状**：0.3.0 / 0.3.1 已处理两个已知坑——桌面版只带 `codebuddy-lite-wb` 精简 bundle（需 `--serve --acp --acp-transport stdio --port 0` 加 `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1`）、CLI 登录态只在单进程内有效（握手后需 `authenticate`，默认 `internal`）。但当前接入仍失败，根因未定位。

**要做的**

- [ ] 先分类定位：找不到 CLI / 握手失败 / 认证被拒（`refusal`）/ 模型目录为空 / `session/prompt` 失败，不同分支对应不同修法。
- [ ] 用 `npm run probe` 直接握手目标 CLI，打印协议版本、模型目录、MCP 能力、登录方式、`session/new` 结果；对照 DSH 侧日志找差异。
- [ ] 核对实际启动参数、`DSH_ACP_WORKBUDDY` 指向、精简 bundle 判定（`dist/codebuddy-lite-wb.mjs` vs `codebuddy-headless.js`）、以及 `DSH_ACP_WORKBUDDY_AUTH` 的登录方式是否适用于当前账号。
- [ ] 修复后逐项对比：DSH 模型菜单里 `acp-workbuddy` 下的模型列表 vs WorkBuddy 客户端显示的可调用模型；费率（是否展示、模型名 / 单价 / 单位、是否随账号变化）逐项记录一致与差异，形成一张对比表。
- [ ] 结论回填 `CHANGELOG.md`；若属兼容性限制，在 `README.md`「已知限制」补一条。

**验收**：WorkBuddy 能在 DSH 正常对话；产出一张模型与费率对比表，差异项注明原因（CLI 未提供 / 插件未透传 / 客户端特有）。

**关联**：`index.js`、`src/connection.js`、`src/index.js`（模型目录注册）、`scripts/probe-acp.mjs`、`README.md`「准备智能体」与「已知限制」。

## 4. 探寻接入模型的额度情况，提供可展开查询的看板

**现状**：插件目前只把 CLI 的模型目录映射成 DSH 模型组，不展示任何额度 / 用量 / 余额信息。

**要核实的**

- [ ] Codex / Qoder / WorkBuddy 各自是否有可读的额度来源：CLI 子命令、本地配置或凭据文件、ACP 扩展方法、桌面版本地接口；记录可用字段（总量、已用、剩余、重置时间、更新时间）与刷新频率。
- [ ] 哪些数据需要账号鉴权、能否在插件进程内读取、有无频率限制或合规风险。

**要做的**

- [ ] 定看板形态（待定）：DSH 内插件面板 / 独立本地 HTML 页面 / CLI 表格输出；要求能按 agent → 模型逐层展开查询，并标注数据时间与来源。
- [ ] 定义数据层：统一额度结构 + 缓存 + 刷新；读不到时明确显示「不可用」，不要编造数值。
- [ ] 若某个 agent 完全不暴露额度，在看板中如实标注，并评估「手动填写额度」作为兜底是否值得做。

**验收**：一个可展开的看板，能查到每个已接入 agent / 模型的额度与更新时间；数据来源与限制写进文档。

**关联**：`src/index.js`（模型目录）、`src/gateway.js`（本地 HTTP 桥接形态可参考）、`scripts/probe-acp.mjs`。

## 5. DSH 是否支持插件通过 GitHub 推送更新

**现状**：现在的升级流程是「先在插件页卸载旧版，再装新版」（`README.md` 与 `docs/安装说明.md` 都这么写），没有自动更新通道；仓库已有 GitHub Actions CI，但发布产物只有 `npm run pack:tgz` 生成的本地包和 `dist/` 里的历史包。

**要核实的**

- [ ] DSH 插件系统有没有版本检查：依据 `package.json` 的 `version`、npm registry，还是安装时记录的来源 URL。
- [ ] 能否声明更新源（manifest / `dsh` 字段 / 仓库 Release），以及是「检查更新 → 提示 → 一键升级」还是必须卸载重装。
- [ ] 若支持 GitHub：确认触发方式（新 Release / tag / 分支推送）、版本比较规则、是否需要签名或校验、依赖更新如何处理。
- [ ] 若不支持：确定替代方案（CI 自动发 Release + `CHANGELOG.md` 提示 + 下载链接），并评估是否值得做一个版本自检脚本。

**验收**：明确「支持 / 不支持」的结论；支持则落地更新配置与发布流程，不支持则把替代升级流程写进安装说明。

**关联**：`package.json`（`version` / `repository` / `dsh`）、`CHANGELOG.md`、`.github/workflows/ci.yml`、`dist/`。

## 6. 整体稳健性、安全性与各 Agent 合规的独立 Review

**现状**：仓库里没有独立的安全与合规审查记录，`README.md`「已知限制」只写功能边界，`CHANGELOG.md` 只记变更。而当前实现里有几处做法需要专门评估：以非公开方式启动桌面版随附的 CLI（`--serve --acp`、注入 `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1`）、凭据透传（`CODEBUDDY_AUTH_TOKEN` / `CODEBUDDY_API_KEY` / `CODEBUDDY_CONFIG_DIR`）、每次连接自动 `authenticate`、`cordis.patch.yml` 中的 `!!js` 表达式、以及 `127.0.0.1` 随机端口的本地 HTTP MCP 网关。

**范围**（独立于具体功能开发，从架构与厂商条款视角整体过一遍）

- [ ] 稳健性：子进程生命周期（超时、取消、崩溃、残留进程）、连接复用与 `maxBindings` / `idleMs` 边界、上下文与输出字节上限被触发时的行为、模型目录为空或 CLI 升级改变目录布局时的降级路径、并发与失败恢复；对照 `test/` 找出覆盖盲区并补测试。
- [ ] 安全性：`cordis.patch.yml` 里 `!!js` 的执行面、环境变量与凭据的透传范围、DSH 会话历史被打包发给第三方 CLI 的数据边界、本地 HTTP 服务的鉴权与暴露面、`execFileSync('reg.exe')` 的输入处理、依赖与供应链（`@agentclientprotocol/sdk`、`vendor/codex-acp`）、日志里是否可能落 token 或提示词。
- [ ] 合规（重点）：逐家核对官方文档与服务条款，确认当前接入方式是否被允许。
  - [ ] **Codex / OpenAI**：CLI 与内置 `@agentclientprotocol/codex-acp` 适配器的使用条款、第三方客户端驱动、账号与凭据使用限制；`vendor/codex-acp` 的 Apache-2.0 授权文件与声明是否完整。
  - [ ] **Qoder**：ACP 文档约定的接入方式、CLI 登录态复用、自动化调用的限制。
  - [ ] **WorkBuddy / CodeBuddy**：桌面版随附的精简 CLI 是否允许被外部程序以 `--serve --acp` 启动、`CODEBUDDY_FORCE_LITE_WB_BUNDLE` 等内部标志的性质、自动 `authenticate` 与凭据透传是否触及账号或反自动化条款、模型与费率信息的展示是否有额外约束。
  - [ ] **交叉项**：把第三方 Agent 包装成 DSH 的「模型提供方」是否违反其对代理、转售、批量调用、多账号的规定；用户数据与提示词跨产品传输的告知义务。
- [ ] 每条结论附依据（官方文档 / 条款原文位置与链接），判定为 `允许` / `需调整` / `禁止` / `待向厂商确认`；不凭猜测下结论，拿不准的列出要向厂商确认的问题清单。

**产出物**：一份独立 review 结论 + 风险台账（风险项 / 等级 / 依据 / 影响范围 / 处置建议 / 状态）；高风险项同步进 `README.md`「已知限制」与 `CHANGELOG.md`。

**验收**：稳健性与安全性问题各有明确处置（修复或接受并记录理由）；三家 Agent 的合规结论都有文档依据，不存在「未核查」的接入方式。

**关联**：`index.js`、`cordis.patch.yml`、`src/*`（尤其 `src/connection.js`、`src/gateway.js`、`src/context.js`、`src/released.js`）、`vendor/codex-acp/`、`LICENSE`、`README.md`「已知限制」。

4. **#4 最后**：依赖前三项产出的模型与账号信息，看板形态还需再定，且额度数据的读取方式受 #6 约束。
